# Отправка расписания от личного аккаунта

Режим подготовлен отдельно от действующего бота. По умолчанию отправитель —
`bot`: наличие личного секрета само по себе ничего не переключает.

## Что сохраняется

- Парсер в GitVerse, получение публичного расписания и GitHub Actions.
- Таблицы, раскрывающиеся дни, расшифровки предметов и подписной календарь.
- Настройки тихого режима и защита от повторных уведомлений.
- Одно обновляемое сообщение. Для личного аккаунта создаётся новая карточка:
  авторство старой карточки бота изменить нельзя.

Личная карточка привязана к конкретным аккаунту, группе и теме. Идентификатор
карточки бота сохраняется отдельно, поэтому можно вернуть прежнего отправителя.
Старое сообщение автоматически не удаляется. После проверки новой карточки
можно отдельно открепить старую.

## Однократное подключение на ПК

1. На https://my.telegram.org/apps создать своё API-приложение.
   Понадобятся `api_id` и `api_hash`; это не токен от BotFather.
2. В корне репозитория выполнить:

   ```powershell
   npm ci --prefix tools/telegram-personal --no-audit --no-fund
   node tools/telegram-personal/login.mjs
   ```

3. В открытом локальном окне ввести данные приложения, номер, код входа и,
   если включён, облачный пароль. Код, пароль и ключи в чат не отправлять.
4. Аккаунт должен состоять в нашей группе и иметь право администратора на
   закрепление сообщений. Анонимная отправка администратора не подходит.
5. Мастер проверит аккаунт, группу и тему, не публикуя ничего в Telegram.
   Затем отключит локальный клиент и сохранит доступ в игнорируемом файле
   `.telegram-personal/credentials.json`. Повторно существующий файл не заменяет.

При поиске приватной группы может потребоваться просмотр метаданных списка
диалогов только на этапе подключения. Остальные диалоги не сохраняются.
В CI используется уже известная группа, без поиска и загрузки чужой переписки.

## Включение в GitHub

1. Содержимое созданного файла сохранить как один Actions Secret
   `TELEGRAM_USER_CREDENTIALS`. Не помещать его в Variables или код.
2. Выполнить ручной workflow **Check personal Telegram without sending**.
   Он проверяет вход и права, не отправляет сообщения и не меняет расписание.
3. Только после успешной проверки установить Actions Variable
   `SCHEDULE_SENDER=user`.
4. Передать свежий снимок через GitVerse с принудительным обновлением.
   Проверить новое сообщение, его автора, закрепление и повторное редактирование.
5. Проверить следующий реальный запуск CI. Успешный ручной запуск не доказывает
   исправность периодического получения расписания в GitVerse.

Доступ личного аккаунта — полноценная сессия, а не разрешение только на группу.
Программа ограничивает себя одной группой и темой; Telegram не делает эту
авторизацию ограниченной. Сессию нельзя печатать в журналах, класть в артефакты,
календарь, кэш расписания или репозиторий. Локальная копия также секретна.

Все использующие сессию CI-запуски сериализованы общей очередью. После создания
файла не запускать параллельно второй локальный клиент с той же сессией.
При ошибках авторизации или лимитах автоматической смены отправителя нет.

## Возврат

Установить Variable `SCHEDULE_SENDER=bot` либо удалить её. Следующее обновление
вернётся к сохранённой карточке бота; удалять токен бота для перехода не нужно.
При отказе от личного отправителя завершить сессию **GASU schedule CI** в списке
устройств Telegram и удалить соответствующий Secret и локальную копию доступа.

## Возможности и границы

Используется mtcute 0.32.7: HTML передаётся серверу без преобразования таблиц
в обычный текст. Для неподдерживаемого rich-сообщения автоматического упрощения
нет: ошибка видна в запуске, текущая карточка не подменяется.

Это не добавляет просмотры конкретной редакции расписания. Сведения о прочтении
новых собственных сообщений в небольшой группе ограничены сроком Telegram.
