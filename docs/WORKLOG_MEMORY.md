# SZS Hub — полный рабочий отчёт и память проекта

Дата актуализации: 3 сентября 2026 года.

Текущее решение см. в разделе 18: живой запуск приостановлен до выбора состава
данных и проверки правовых оснований. Старый порядок «сначала оплатить VPS» ниже
больше не является актуальным следующим шагом.

Этот файл создан как долговременная память о работе в текущем чате. Он нужен, чтобы
в следующей сессии не восстанавливать контекст по фрагментам переписки и не повторять
уже выполненную работу. В нём отдельно указаны факты, причины решений, способы
реализации, проверки и оставшиеся внешние шаги.

## 1. Цель проекта и принятый масштаб

SZS Hub — закрытый Telegram-бот для учебной группы СПбГАСУ примерно из 30 человек.
Основные функции:

- публикация расписания и понятных изменений в нём;
- отметка присутствия реакцией и личная сводка старосте;
- архив сообщений и материалов группы с локальным поиском;
- аккуратное копирование учебных материалов в фиксированную тему;
- приватный AI-помощник, который отвечает по архиву и показывает источники;
- работа после перезапусков без потери принятых Telegram-обновлений;
- дешёвое размещение на одном VPS без публичного входящего веб-сервера.

Ключевая коррекция масштаба была сделана после длительного security-review: это не
публичный SaaS и не банковская система. Поэтому приоритет — простая эксплуатация,
сохранность данных группы, ограниченный AI-бюджет и отсутствие очевидных утечек.
Редкие сценарии, требующие отдельной распределённой платформы, зафиксированы как
известные ограничения, но не блокируют подготовку маленького закрытого проекта.

## 2. Исходное состояние и организация репозитория

Рабочий репозиторий: `szs-hub`, ветка `main`.

На момент этого отчёта файлы проекта существуют локально, но Git показывает их как
неотслеживаемые. Коммиты не создавались, потому что в окружении не задана Git-личность
владельца, а придумывать автора или почту нельзя. Перед реальным релизом владелец должен
сам настроить `user.name`/`user.email`, проверить изменения и сделать исходный commit/tag.

Каталог `sources/` родительского ChatGPT-проекта использовался только как справочный и
не изменялся.

Проект оформлен как Python 3.12 modular monolith:

- `src/szs_hub/` — приложение;
- `alembic/` — миграции SQLite;
- `tests/` — модульные и интеграционные тесты;
- `deploy/` — systemd, runtime/backup env-примеры и backup-скрипты;
- `docs/` — архитектура, эксплуатация, privacy, deployment и ограничения;
- `COST.md` и `SECURITY.md` — бюджет и границы безопасности.

Причина такого устройства: для 30 пользователей один процесс и SQLite проще, дешевле и
надёжнее в эксплуатации, чем Docker/Kubernetes, PostgreSQL, брокер сообщений и отдельные
микросервисы.

## 3. Архитектура и надёжность Telegram-бота

Выбрана работа через Telegram long polling. Публичный порт, домен, TLS-сертификат и
webhook для первой версии не нужны. Это уменьшает стоимость и количество точек отказа.

Реализованы:

- durable inbox для сырых Telegram updates;
- уникальность по `update_id`, чтобы повторное получение не создавало вторую запись;
- отдельные устойчивые очереди core/material jobs;
- leases, attempts и backoff для восстановления после падения worker;
- transactional outbox для Telegram-отправок;
- семантические idempotency keys для расписания, посещаемости и материалов;
- сохранение Telegram message ID после успешной отправки;
- heartbeat, health CLI и периодическая проверка прав бота/членства старосты;
- process lock, не допускающий два конкурентных экземпляра с одной SQLite.

Почему это сделано: Telegram и SQLite нельзя объединить одной транзакцией. Сначала
обновление надёжно сохраняется локально, потом выполняется бизнес-логика, а отправки
выносятся в outbox. После рестарта очередь продолжает работу.

Оставшееся ограничение: если Telegram принял сообщение, но подтверждение потерялось до
локальной фиксации, возможен повтор. Telegram не предоставляет общий idempotency header.
Для закрытой группы этот редкий сценарий принят: число попыток ограничено, а полностью
устранять его пришлось бы сложной сверкой удалённого состояния.

## 4. Расписание СПбГАСУ

Реализован клиент публичного расписания СПбГАСУ:

- запрос только конкретной группы;
- поддержка реально наблюдённого параметра `SERACH` с опечаткой источника;
- разбор корневой структуры и обёртки `R`;
- загрузка номера учебной недели и списка групп со страницы bootstrap;
- числитель/знаменатель и официальные временные слоты;
- неизменяемые snapshots, hash и semantic diff;
- публикация только понятных пользователю изменений;
- last-known schedule со временем получения при недоступности источника;
- cache и ограниченные retries.

В ходе финальных исправлений HTTP-ответы переведены на потоковое чтение. Лимит байтов
проверяется во время чтения, до JSON/text materialization. Это предотвращает заполнение
памяти чрезмерным ответом внешнего сайта.

Что не сделано: авторизованный/заочный Bitrix-flow сайта СПбГАСУ. Его нельзя угадывать.
Нужен реальный Network capture после входа владельца в браузере: URL, метод, form fields,
cookies/session lifecycle и формат ответа.

## 5. Посещаемость и права старосты

Реализованы:

- карточка пары и окно реакции;
- идемпотентное добавление/снятие выбранной реакции;
- игнорирование поздних, анонимных и неподдерживаемых событий;
- закрытие сессии и сводка старосте;
- повторное редактирование одной сводки вместо создания множества сообщений.

Security-review обнаружил, что после успешного старта бывший староста теоретически мог
продолжить получать личные сводки. Исправление сделано в общей точке отправки:

- каждый положительный private `chat_id` должен совпасть с текущим `HEADMAN_USER_ID`;
- непосредственно перед отправкой выполняется актуальный membership check;
- неизвестное состояние, API-ошибка, LEFT/KICKED и старый ID fail closed;
- подтверждённая ошибка конфигурации в периодической проверке останавливает unsafe
  automation, после чего systemd перезапускает приложение через startup probe.

Так закрывается не только уход старосты, но и уже поставленное в очередь сообщение для
старого ID после изменения конфигурации.

## 6. Архив, поиск и импорт истории

Реализованы:

- live ingestion новых сообщений и edits только из целевой группы;
- сохранение reply/media/topic metadata;
- SQLite FTS5/BM25;
- нормализация русского текста: Unicode NFKC, casefold, `ё→е`, пунктуация, Snowball
  stems и aliases;
- фильтры по автору, теме, дате и типу;
- Telegram Desktop JSON planning и безопасный offline apply;
- fingerprint SHA-256 исходного export;
- обязательный backup, exclusive process lock, resume state, reconciliation и audit;
- запрет traversal для media paths.

Импорт не выполнялся на реальном пользовательском export: его ещё не предоставляли.
Текущий import в основном сохраняет метаданные/ссылки; исходный export нельзя удалять до
отдельного решения о переносе реальных media-файлов.

## 7. Материалы и извлечение документов

Реализованы:

- сбор одиночных сообщений и albums;
- прозрачная классификация учебного материала;
- low confidence — ничего не менять;
- medium confidence — отправлять тихую проверку старосте;
- high confidence — копировать только в фиксированную тему материалов;
- подтверждать полный результат copy/copy_messages;
- исходные сообщения никогда автоматически не удалять.

Добавлено bounded extraction для TXT/PDF/DOCX/XLSX/PPTX:

- MIME/magic/OOXML проверки;
- запрет symlink, traversal, duplicate/encrypted entries и compression bombs;
- лимиты файла, страниц, XML, ячеек, текста, изображений и времени;
- временный приватный каталог и cleanup;
- content hash, extracted text и `needs_ocr`;
- повторная индексация и reassessment материала.

Extraction по умолчанию выключен. Причина: библиотечный parser работает внутри процесса
бота и не является killable OS sandbox. Для первой production-версии документы можно
индексировать по Telegram metadata; extraction включать после отдельного изолированного
worker на реальном Linux-host. OCR пока не реализован.

## 8. AI-помощник

Реализованы:

- replaceable OpenAI-compatible provider;
- текущая membership authorization до поиска и до отправки данных провайдеру;
- bounded FTS retrieval и ограниченный контекст;
- system prompt, который считает архивные сообщения недоверенными данными;
- ссылки `[S1]`, `[S2]` на исходные Telegram messages;
- короткая conversation memory с TTL;
- AI kill switch, не влияющий на расписание, посещаемость и локальный поиск;
- безопасные сообщения об ошибках без provider body/API key;
- потоковое чтение provider response с лимитом;
- ограничение сохраняемого ответа 4096 символами.

Изначально quota была только общей дневной. Теперь есть:

- общий дневной request/token limit;
- персональный дневной request limit;
- общий calendar-month request/token limit;
- conservative token reservation до сетевого запроса;
- reconciliation только когда провайдер вернул оба корректных неотрицательных token
  counters; неполная статистика не уменьшает резерв;
- production/staging требуют HTTPS;
- неоднозначные billable retries в production запрещены до поддержки provider
  idempotency (`AI_MAX_RETRIES=0`).

В коде пока нет точного RUB-счётчика: тарифы моделей меняются, а provider invoice является
источником истины. Жёсткий token cap и kill switch уже ограничивают потребление; реальный
RUB alert/stop нужно связать с API выбранного провайдера после создания аккаунта.

Рекомендованный первый провайдер: DeepSeek direct, OpenAI-compatible endpoint
`https://api.deepseek.com`, дешёвая модель Flash. OpenRouter оставить запасным вариантом,
если прямая регистрация/оплата окажется неудобной.

## 9. Privacy и retention

Реализован ежедневный bounded retention job:

- redaction обработанных raw Telegram payloads после 30 дней;
- redaction failed update/job/outbox diagnostics после 90 дней;
- после исправления failed raw update payload также очищается после 90 дней;
- удаление AI conversation/messages после 30 дней неактивности;
- повторный запуск идемпотентен и работает партиями.

Не реализованы person-level attendance erasure/export, полная академическая retention
политика и scoped legal/security holds. Для проекта на 30 знакомых пользователей это
зафиксировано как последующая privacy-функция, а не причина задерживать инфраструктуру.

## 10. Развёртывание, здоровье и резервные копии

Подготовлены systemd units для:

- основного бота;
- migrations;
- doctor;
- health;
- encrypted backup;
- fixed-code owner alerts.

Units запускаются от отдельных non-root accounts, без capabilities, с ограниченными
filesystem paths, address families, tasks, descriptors и memory. Docker не требуется.

Подготовлен backup pipeline:

- SQLite Online Backup API вместо копирования живого DB-файла;
- `quick_check`;
- compression;
- локальное шифрование `age` до upload;
- SHA-256 verification;
- rclone upload;
- 7 daily + 4 weekly + 3 monthly generations;
- restore runbook.

Security-review выявил, что backup account состоял в state group, а `runtime.env` был
group-readable. Поэтому backup account мог прочитать Telegram/AI secrets. Исправлено:
`runtime.env` устанавливается `root:root 0600`; systemd читает EnvironmentFile как root до
запуска непривилегированного процесса. Backup account сохраняет только доступ к SQLite.

Это нужно подтвердить уже на VPS командами:

```sh
sudo systemd-analyze verify /opt/szs-hub/current/deploy/systemd/*.service
sudo -u szshub-backup test ! -r /etc/szs-hub/runtime.env
sudo -u szshub-backup test -r /var/lib/szs-hub/szs_hub.sqlite3
sudo systemctl start szs-hub-doctor.service szs-hub-health.service
```

Remote object lock не подтверждён. Для маленького проекта достаточно начать с
зашифрованных versioned backups и обязательного restore drill; усиление bucket IAM/object
lock можно добавить после успешного первого развёртывания.

## 13. Браузер и Computer Use

Попытки подключить Windows Computer Use/Chrome дважды завершились `EPERM` при доступе к
пути Codex app. Настройки безопасности не обходились. Поэтому фактический авторизованный
Network flow сайта СПбГАСУ пока не снят.

Правильный следующий способ:

1. владелец присылает только URL и указывает нужную страницу/группу;
2. по возможности создаёт временный аккаунт с минимальными правами;
3. владелец самостоятельно входит в Chrome, не отправляя пароль в чат;
4. после входа Codex через browser session изучает Network requests;
5. если Chrome integration снова недоступна, владелец делает sanitised HAR без Cookie,
   Authorization, password и session tokens либо показывает структуру запроса;
6. parser реализуется только по наблюдённому протоколу, с timeout/limits/session refresh и
   fixtures, а не по догадке.

## 14. Рекомендованная инфраструктура

Для первой staging/production итерации выбран простой вариант:

- один российский VPS;
- Ubuntu/Debian с systemd, Python 3.12 и локальным SSD;
- один процесс SZS Hub через long polling;
- SQLite/FTS5 на локальном диске;
- swap для бюджетного 1 GB host;
- AI только удалённый, extraction выключен;
- encrypted backup в Yandex Object Storage.

Текущий практичный вариант — RUVDS START HIT SSD: 1 vCPU, 1 GB RAM, 20 GB SSD. Если
document extraction/OCR понадобится в production или появится memory pressure, перейти на
2 GB RAM. Ранее исследованный 4VPS 2 GB остаётся кандидатом, но перед оплатой цена и
доступность должны быть повторно подтверждены на официальном сайте.

Предлагаемый AI:

```env
AI_PROVIDER=openai_compatible
AI_BASE_URL=https://api.deepseek.com
AI_MODEL=deepseek-v4-flash
AI_MAX_RETRIES=0
AI_MAX_RESPONSE_BYTES=1000000
AI_KILL_SWITCH=true
AI_DAILY_REQUEST_LIMIT=100
AI_DAILY_TOKEN_LIMIT=100000
AI_PER_USER_DAILY_REQUEST_LIMIT=10
AI_MONTHLY_REQUEST_LIMIT=1000
AI_MONTHLY_TOKEN_LIMIT=1000000
AI_TOKEN_RESERVATION_PER_REQUEST=3000
```

Сначала `AI_KILL_SWITCH=true`; включать после staging-вопросов, проверки источников,
русского качества, provider retention terms и баланса.

## 15. Какие данные ещё нужны от владельца

Не передавать пароли, bot token, API key, session cookies и backup credentials сообщением
в чат.

Нужны несекретные данные:

- подтверждение хостинга: RUVDS/4VPS/другой;
- URL сайта расписания и точное название/ID группы;
- какие страницы доступны только после входа;
- Telegram forum group и названия нужных topics;
- numeric IDs получать только из staging/runtime, не угадывать;
- желаемый AI provider и фактический месячный бюджет;
- нужен ли import старой Telegram history и сохранение media.

Секреты вводятся владельцем напрямую:

- `/etc/szs-hub/runtime.env` через `sudoedit` на VPS;
- `/etc/szs-hub/backup.env` и закрытый `rclone.conf`;
- login/password сайта — владельцем в браузере;
- API keys — в provider console и runtime.env, не в Git.

## 16. Следующие действия по порядку

1. Владелец настраивает Git identity и делает исходный commit после просмотра файлов.
2. Выбирается и оплачивается VPS; ставится актуальная Ubuntu/Debian.
3. Создаются отдельные staging bot и disposable Telegram forum group.
4. На VPS устанавливаются release, systemd units и root-only runtime.env.
5. Запускаются `doctor`, migrations, health и проверка SQLite version/WAL.
6. Проверяются Telegram long polling, topics, reactions, private `/start` и membership.
7. Проверяется реальный SPbGASU public request с IP выбранного VPS.
8. Создаётся DeepSeek key, но AI остаётся выключенным до smoke tests.
9. Настраивается encrypted Yandex backup и выполняется полный restore drill.
10. Проводится 3–7-дневный staging/burn-in для этого маленького проекта.
11. Владелец входит на нужный сайт; снимается Network flow и пишется parser.
12. После приёмки staging используются отдельные production bot/group identifiers.

## 17. Состояние завершённости

Локальная кодовая база является хорошо протестированным release candidate, но не может
честно называться работающей production-системой без внешних аккаунтов и staging.

Готово локально: архитектура, storage/migrations, Telegram durability, schedule parser,

## 19. Выбран и реализован режим «только расписание» — 03.09.2026

Владелец отказался от персональных функций первого выпуска и выбрал единственную задачу:

и реализован локально.

Что изменено и зачем:

- добавлен явный `FEATURE_PROFILE=schedule_only`, который является безопасным профилем
  по умолчанию; старый функционал сохранён за отдельным значением `full` для будущей
  разработки, но не включается случайно;
- для него добавлен отдельный `TELEGRAM_MODE=outbound_only`; несовместимая комбинация
  профиля и транспорта блокируется до любых подключений;

  файлы, реакции или Telegram ID студентов;
- при старте удаляются накопленные Telegram updates. Это не даёт старым сообщениям
  попасть в приложение на старте; новые updates приложение не запрашивает. Будущий
  полный режим должен использовать отдельного бота и отдельную БД;
- разрешены только задания синхронизации расписания, вечерней публикации и технического
  heartbeat. Создание attendance jobs выключено;

- sender повторно проверяет исходящие задания и отвергает всё, что не является карточкой

  выполнения старого задания из иной конфигурации;
- имена преподавателей удаляются до сохранения снимка расписания и не публикуются;
- в минимальном профиле бот больше не обязан быть администратором: достаточно обычного

  публичного запроса с VPS и тестовой публикации в отдельной теме.

Добавлены тесты границы: минимальная non-local конфигурация без личных ID; отсутствие
Telegram update ingestion; только schedule/heartbeat jobs; отсутствие лишних полей в

## 24. Rich Message, недельный обзор и тихое отслеживание — 11.09.2026

После первой подтверждённой Telegram-доставки владелец попросил заново продумать вид,
частоту и смысл уведомлений. По актуальной официальной документации Telegram проверен

details-блоки, футеры и цветные кнопки непосредственно в forum topic. Это и есть новый
нативный «режим статьи»; внешний Telegraph не нужен и сделал бы приватное расписание
доступным по отдельной публичной ссылке. Эффекты сообщений работают только в личных
чатах, checklist не соответствует расписанию, а custom emoji создаёт зависимость от
Premium, поэтому эти функции сознательно не добавлены.

Вечерняя карточка переработана: сразу виден завтрашний день, пары представлены
компактной таблицей «время / предмет / где», ниже указан диапазон учебного дня. Следующие
семь дней спрятаны в раскрываемом блоке, поэтому сообщение одновременно информативно и
не выглядит простынёй. Внизу находятся время проверки, группа, источник и одна кнопка
на официальное расписание. Отправка сначала использует Rich Message, а при ответе
Telegram HTTP 400 автоматически возвращается к проверенной обычной HTML-карточке.

Владелец показал реальный результат: ночью в пятницу бот уже смотрел на субботу и писал

неотличим от настоящего свободного дня.

Выбор дня исправлен так: до 20:00 МСК принудительная/дневная карточка показывает сегодня,
с 20:00 — завтра. Основной блок остаётся коротким, следующие семь дней помещены в

мог отправить старую карточку «Завтра» со ссылкой, удалён.

Текущий публичный запрос был восстановлен по JavaScript самого сайта. Страница вызывает
Bitrix class action `gasu:raspisanie.csv/getRasp` через

После независимого ревью парсер дополнительно переведён в fail-closed режим. Если хотя
бы один содержащий занятия блок потерял дату, распознаваемую чётность, номер пары,

уведомления об отмене реальных занятий при очередном изменении HTML.

Реализованы спокойные напоминания без постоянно работающего ПК или сервера:

- примерно за два часа до первой пары приходит время, предмет и место;
- ближе к окончанию текущей пары сообщение показывает, через сколько следующая, её
  точное время, предмет и аудиторию/корпус;
- после последней пары сообщение не отправляется;
- полный идентификатор `3-СУЗСс-3` не дублируется в карточке, но настоящая подгруппа
  остаётся видимой;
- маркеры уже отправленных событий сохраняются вместе с расписанием и предотвращают
  повтор в штатном CI-cache.

GitHub reminder workflow запускается только в конечном наборе моментов, вычисленном из
официальных семи интервалов звонков: все варианты «первая пара минус два часа» и переходы
«конец пары минус 15 минут». Окна допуска немного расширены на случай обычной задержки
GitHub scheduler; текст всегда показывает фактически оставшееся время. Receiver и
reminder используют общую concurrency-группу с `queue: max`, поэтому ожидающие запуски
не вытесняют друг друга. Cache переведён на ключ `schedule-state-v2`, отделив старый
ошибочный baseline. Снимок с `fetched_at`, который не новее сохранённого, игнорируется,
чтобы одновременно запущенные GitVerse jobs не откатили расписание назад.

Для ручного исправления `force_digest=true` теперь имеет специальную семантику чистого
rebaseline: бот отправляет ровно одну запрошенную карточку и не сравнивает её с прежним
пустым снимком. Иначе первая правильная загрузка могла бы сначала прислать ложную стену
«все пары добавлены», а затем саму карточку.

уникальности lesson IDs, принудительного rebaseline, защиты от старого снимка, UTC→МСК,
адресации Telegram chat/topic, успешной и неуспешной записи reminder marker,
дедупликации, настоящих подгрупп, полного множества cron и отсутствия URL во всех

Текущая эксплуатационная граница сознательно проста: Actions cache не является

пропуск напоминания до следующего полученного снимка или один дубликат. Для бесплатного

### 15.09.2026 — мобильная сетка одной пары

По обратной связи владельца расписание переведено с одной длинной ячейки на составную
табличную карточку. Время слева центрировано по горизонтали и вертикали и объединяет три
строки через `rowspan`. Справа предмет занимает верхнюю строку через `colspan`; следующая
строка разделяет тип занятия, аудиторию и корпус по отдельным ячейкам; полное ФИО занимает
всю нижнюю ширину. Для отличающейся подгруппы добавляется отдельная широкая строка.
Так переносы остаются локальными и предсказуемыми на узком телефоне, а место можно найти
взглядом, не разбирая строку из разделителей.

уменьшенные отступы. Добавлены регрессии структуры основной карточки и условной строки
